## 1. 评测还会被做虚的地方

### 1.1 `cause` 仍是开放字符串

类别有枚举，具体原因没有。模型写成 “connection pool exhausted”，场景里是 `db_pool_exhausted`，Top-1 就落空。`acceptable_alternatives` 只能靠出题人把同义词列全。

`cause` 改为分类表里的 id，精确匹配。自然语言放到不参与评分的 `cause_summary`。

### 1.2 `NOT_A_FAULT` 和 `UNKNOWN` 写了两次

它们既在 `verdict` 里，又在类别枚举里。流量突增可以标成类别 `TRAFFIC`、结论 `NOT_A_FAULT`，也可以标成类别 `NOT_A_FAULT`，两次都算对或都算错。

类别只描述机制：`CPU`、`MEMORY`、`DISK`、`DATABASE`、`NETWORK`、`DEPENDENCY`、`DEPLOY`、`CONFIG`、`TRAFFIC`。`verdict` 才是 `FAULT`、`NOT_A_FAULT`、`UNKNOWN`。后两个结论不评 Top-3，也不评 `severity`，`severity` 留空。评分比较报告里的 `severity` 和场景期望，与用户填在事件上的 `user_severity` 无关。

### 1.3 非法引用重试会把幻觉率洗成 0

FR-5 规定引用不在账本里就拒绝并重试一次。门禁若只看重试后的报告，模型每次瞎编都会被代码抹掉，0% 只说明校验器在工作。

幻觉率统计第一次输出。重试后仍不合法，Run 记为 `FAILED`，`final_report` 为空，评测记错。

### 1.4 +20 个百分点不该是主结论

规则基线若只用通用阈值，具体原因的准确率会很低，模型只要能读日志就能涨二十个点。能说明「会调查」的数字是 **M4 减去 M3**：同样的证据，差别只在于程序全部喂进去，还是模型自己选工具。

相对规则基线的差值照实记录。基线 Top-1 低于 30% 时，不把 +20 个百分点写成失败条件。基线高于或等于 90% 时加难，这一条保留。

### 1.5 M3 的工具参数没有归属

按场景手写「最佳查询」会让对照组偷看答案。M3 由代码生成参数：

- 拓扑里的每个服务
- 每个指标枚举值
- 一个由事件时间决定的窗口（见 §2.4）
- 日志使用固定查询，例如 `level>=ERROR`

不允许按题写查询。M1 到 M5 的工具集不含 `search_memory`。M6 加入该工具之后，不再把新结果拿去和已经发布的 M3/M4 分数直接相减。

### 1.6 证据键不能带着答案标签

工具结果只放证据键和数据，不放 `relevant: true` 这类标签。`ground_truth` 只有评分器能读。

两个分数分开算：

- 引用是否在账本里：代码校验，看的是有没有编造。
- 证据精确率：`|引用键 ∩ 期望键| / |引用键|`。红鲱鱼键在账本里是合法引用，但会拉低精确率。

### 1.7 调 Prompt 时不能看完全部题

参数化生成的题可以用来练习。对外报告的分数只来自事先冻结的题集，其中至少 6 题在调 Prompt 期间不打开。

## 2. 和里程碑冲突的两句

### 2.1 M1 写着「分数入库」，数据库在 M2

M1 的验收改为把基线分数写入文件，例如 `evals/baselines/`。Postgres 仍从 M2、随第一张表出现。

### 2.2 合并门禁和回放说明互相打架

回放永远得到录音里的那次诊断，所以 Pull Request 上的 Top-1 不会因为模型变差而变红。FR-8 把 Top-1 写成合并门禁，同节又写夜间真实模型才代表 Prompt 质量。拆开：

| 时机 | 失败条件 |
| --- | --- |
| 每次 Pull Request | 单元测试、规则基线、回放结果与录音一致、引用校验器本身通过 |
| 夜间真实模型 | Top-1、证据键召回与精确率、`agreement@k`。报告留档，不阻断合并 |

作品集项目里，夜间失败用来解释波动，不卡住合并。

## 3. 实现时还会各自猜测的细节

1. **评测与跨 Run 继承。** 同一事件的新 Run 默认继承上一轮已排除的假设。评测若复用同一个 `incident_id`，重复跑 k 次就不再独立，`agreement@k` 会偏高。评测用例每次使用新事件，或强制关掉跨 Run 继承。评测请求不带 `Idempotency-Key`。
2. **Trace 回放。** `GET /v1/runs/{id}/events` 从 `seq=0` 回放，并支持 `Last-Event-ID`。只推新事件的话，UC-3 无法回放已经结束的 Run。`GET /v1/runs/{id}` 返回最终状态和 `final_report`。
3. **多次 Run 之后的事件状态。** 有报告（含半成品）就标 `DIAGNOSED`。没有报告的 `FAILED` 或 `CANCELLED` 保持 `INVESTIGATING`。已经 `RESOLVED` 之后仍允许再跑，状态不自动退回。
4. **`partial` 反馈。** 记忆保持原信任等级，不晋升，也不拒绝。
5. **默认时间窗。** 有 `occurred_at` 时，用它的前 15 分钟到 `detected_at` 后 5 分钟。没有则用 `detected_at` 前 30 分钟。评测用例里 `service` 和时间必填。API 上 `service` 可以空；空了才允许模型补，并在 Trace 里标明「由模型推断」。
6. **异步。** `LLMPort` 的调用是异步的。单进程里如果用同步的模型 SDK，多个 Run 会把事件循环堵死。
7. **CLI 没有里程碑。** 决策已写「先 API + CLI」，路线图没有归属。放到 M2：一个命令提交事件、接上事件流、打印报告。

第 9 节的提供商不用卡住文档。M3 再填手头有密钥的那一家。
